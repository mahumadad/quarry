# CVEngine — Referencia

> Plataforma de attack surface assessment con discovery continuo y
> validación basada en evidencia.
> Repo: github.com/hevnsnt/CVEngine (fork de reNgine 2.x, 477 stars)
> Usado como referencia de diseño, no como dependencia.

## Qué es

Producto completo (Django + Celery + PostgreSQL + Redis en Docker Compose,
~880 archivos). Pipeline de 13 etapas secuencial: bbot discovery → nmap →
nuclei tech pass → WAF fingerprint → version probes → CVE correlation →
nuclei AI-targeted pass → triage/validation. Un **conductor** mantiene la
cola de trabajo llena automáticamente, priorizando por staleness.

Modelo multi-tenant con roles, MFA, y servidor MCP (127 tools sobre
JSON-RPC 2.0 Streamable HTTP).

## Ideas adoptadas para el plugin

### 1. Fire/Smoke/Ice priority classification

Clasificación determinista de prioridad temporal que combina CVSS + EPSS +
CISA KEV + exploits públicos en tres tiers de acción:

| Tier | Señal | Acción |
|------|-------|--------|
| Fire | KEV, exploit público, EPSS > 0.7 | P1 inmediato |
| Smoke | CVSS ≥ 7 + EPSS > 0.1, PoC sin verificar, version match | Investigar esta fase |
| Ice | Sin señales de explotación | Backlog |

**Implementación**: `engine/priority.py` — función pura sobre datos que
ya recolectamos (CVSS, EPSS, KEV de `cvss4-epss-kev.md`). Se integra con
`FindingsStore` vía `classify_finding()`.

### 2. Automated validation pipeline

Checks read-only que re-verifican findings para promover automáticamente
de Inferred → Demonstrated (o demover a Killed):

- **nuclei_targeted**: template específico contra el endpoint del finding
- **nmap_version**: `-sV` para confirmar versión exacta
- **banner_grab**: headers de respuesta para confirmar producto
- **http_head**: re-request para verificar que la vuln sigue presente
- **version_probe**: probe del catálogo de version-probes.md
- **certificate_check**: cadena de certificados y cipher suites

**Implementación**: `engine/validation.py` — genera plan de validación
por finding, ejecuta checks, evalúa resultados con reglas deterministas.
Killings requieren human gate.

### 3. AI nuclei template generation

Genera templates nuclei on-the-fly para CVEs sin template existente:

1. Extrae endpoints y strings de detección del advisory
2. Genera YAML con skeleton GET-only + AND matchers
3. Valida sintaxis y reglas de calidad
4. Guarda en directorio `autogenerated/` separado de templates revisados

**Implementación**: `engine/templategen.py` — genera desde TemplateSpec
o desde advisory text. Templates autogenerados llevan
`metadata.reviewed: false` y `metadata.autogenerated: true`.

### 4. Version probes catalog

Catálogo de probes read-only para detectar versiones exactas de software
sin payloads. Reduce falsos positivos en correlación CVE.

**Implementación**: `references/version-probes.md` — 40+ probes
organizados por categoría (web servers, frameworks, databases, CMS,
network, TLS). Se usan en recon (tech fingerprint), CVE correlation
(version match = Smoke signal), y validation (VERSION_PROBE checks).

### 5. MCP server (diseño, no implementado)

CVEngine expone 127 tools MCP bien tipados. Para el plugin, la idea es
exponer como tools MCP:
- `list_findings` / `get_finding` — consultar findings del engagement
- `get_scope` — scope activo
- `list_chains` — chains descubiertas
- `get_priority` — clasificación Fire/Smoke/Ice de un finding
- `run_validation` — ejecutar validation plan de un finding
- `engagement_summary` — resumen del engagement

**Estado**: diseño. No implementado aún — requiere decisión sobre
transporte (stdio vs HTTP) y autenticación.

## Qué NO adoptamos

- **Django/Celery/PostgreSQL stack** — somos un plugin de Claude Code,
  no una webapp. Nuestro estado es JSON en disco + custody log.
- **Conductor/scheduling continuo** — nuestro modelo es engagement-driven,
  no continuo. El operador decide cuándo y qué escanear.
- **Sentinels (scanners distribuidos)** — nuestro Docker lab (torgw+kali)
  es suficiente para nuestro caso de uso.
- **Bug bounty workflow** — manejamos scope genérico, no scope por
  programa HackerOne.
- **Multi-tenancy** — single-operator plugin.
